# EggDB v0.3 — Write Support

## Goal

INSERT, UPDATE, and DELETE rows in a `.egg` file without hatching it back to
SQLite. Writes must be crash-safe, transactional, and visible to every command.
The `.egg` main file format (version 1) does not change.

| Feature | Format Change | User-Visible Result |
|---------|---------------|---------------------|
| Write log (`data.egg.wal`) | New sidecar file, main format untouched | Edits never modify the main file |
| Writable virtual table | None | `INSERT/UPDATE/DELETE` via `egg query`, `egg shell`, any SQLite client |
| Constraint enforcement | None | Writes that would break `egg hatch` fail immediately |
| `egg compact` | Produces a normal v1 `.egg` | Folds changes in, restores full compression |
| Log-aware reads | None | `crack`, `hatch`, `info`, ... all show pending changes |

## Why Not the v0 Roadmap Sketch

The v0 roadmap proposed a hot buffer that is itself a valid `.egg` file, plus a
separate `.egg.del` delete bitmap. Four facts in the code rule that out:

1. **A `.egg` cannot be appended to.** The header CRC32C covers every byte of the
   file and `write_egg()` builds the whole file as one `Vec<u8>`. An insert into a
   `.egg`-format buffer rewrites the entire buffer: O(buffer) per row, which
   contradicts the "< 10 µs per row" target in the same sketch.
2. **The albumen is untagged bincode v1.** Adding a field to `ColumnMeta` or
   `TableMeta` (e.g. `deprecated: bool`) breaks deserialization of every existing
   file, forcing format version 2. Keeping all write state in a sidecar keeps
   format v1 frozen.
3. **Two sidecars cannot be updated atomically.** Inserts in `.wal` and deletes in
   `.del` would need their own cross-file crash protocol. One ordered log gives
   atomicity for free.
4. **rusqlite 0.31 hard-codes `xBegin/xSync/xCommit/xRollback` to `None`** for
   writable vtables, so `ROLLBACK` cannot undo egg writes. rusqlite 0.40 adds
   `TransactionVTab` and `update_module_with_tx`.

## Architecture

```
data.egg        immutable main file, format v1, never modified in place
data.egg.wal    append-only write log (created on first committed write)

read     = decode main columns  ->  replay log into per-table overlays  ->  merge
commit   = append one frame (all ops of one transaction)  ->  fsync
compact  = merged rows -> re-analyze + re-encode -> temp file -> fsync -> rename
```

### Crate Layout

```
eggdb-core     + format/wal.rs       log header/frame encode + parse (pure bytes)
               + format/overlay.rs   TableOverlay: replay ops, merge with base columns
               + format/rebuild.rs   decode -> analyze -> encode (moved out of relay CLI)
eggdb-store    NEW: std::fs + eggdb-core. Snapshot open, locked append, compaction.
eggdb-vtable   + UpdateVTab + TransactionVTab, constraint validator. Depends on core + store.
eggdb-io       hatch reads through eggdb-store snapshots. Depends on core + store + rusqlite.
CLI            + `egg compact`; query/shell writable; all read paths log-aware.
```

`eggdb-store` exists because the log's file IO (locking, fsync, atomic rename,
crash recovery) is needed by the vtable, `eggdb-io`, the CLI, and the Python
bindings. `eggdb-core` must stay IO-free, and `eggdb-vtable` must not depend on
`eggdb-io`. Duplicating crash-safety code across crates is not acceptable.

Boundary rules after this change:
- `eggdb-core`: no IO (unchanged)
- `eggdb-store`: depends on `eggdb-core` only. No rusqlite.
- `eggdb-vtable`: depends on `eggdb-core` + `eggdb-store` (not `eggdb-io`)
- `eggdb-io`: depends on `eggdb-core` + `eggdb-store` + rusqlite
- `eggdb-yql`: no eggdb deps (unchanged)

## M13: Write Log + Overlay (eggdb-core, pure)

### Log File Layout

All integers little-endian.

```
HEADER (32 bytes)
  [0..4]    magic: b"EGGW"
  [4]       version: u8 = 1
  [5..8]    reserved: zero
  [8..12]   base_checksum: u32    main file's header CRC32C (bytes [50..54])
  [12..20]  base_length: u64      main file's byte length
  [20..28]  reserved: zero
  [28..32]  header_crc: u32       CRC32C of bytes [0..28]

FRAMES (repeated until EOF)
  [0..4]    payload_len: u32
  [4..8]    frame_crc: u32        CRC32C of payload_len bytes ++ payload
  [8..]     payload: bincode(Frame), same bincode config as the albumen
```

`base_checksum` + `base_length` bind the log to exactly one generation of the
main file. A log whose base does not match the main file is never silently
applied or silently ignored (see M14 recovery table).

### Frame Types

```rust
enum Frame {
    /// One committed transaction. `seq` increases by 1 per Commit frame.
    Commit { seq: u64, ops: Vec<Op> },
    /// Cancels the immediately preceding Commit (rollback after xSync).
    Revert { seq: u64 },
    /// Compaction wrote a new main file with this checksum + length.
    Compacted { checksum: u32, length: u64 },
}

enum Op {
    Insert { table: u32, row: Vec<Value> },
    Update { table: u32, rowid: u64, row: Vec<Value> },
    Delete { table: u32, rowid: u64 },
}
```

### Parse Rules

- Header magic/version/reserved/CRC must be valid, else error. Exception (in
  `eggdb-store`): a file no longer than a header whose header is invalid is an
  interrupted log creation (frames are only appended after the header is durable)
  and reads as "no log".
- The frame CRC covers the length bytes too, so a damaged length is detected
  whenever the frame lies inside the file.
- A frame that is incomplete (fewer bytes than `8 + payload_len`), **or** has a
  CRC mismatch and either ends exactly at EOF or is followed only by zero bytes
  (a filesystem extended the file before the data landed), is a torn tail from a
  crash mid-append. It is discarded and reported via `torn_tail_bytes`.
- A CRC mismatch on a frame followed by other data is corruption: error.
- A CRC-valid frame whose payload does not decode was written by an incompatible
  writer: error, never treated as torn.
- Residual risk (same class SQLite accepts): a bit flip in a middle frame's length
  that points past EOF is indistinguishable from a torn tail. `egg validate`
  reports discarded tail bytes, so it is visible.
- `payload_len` larger than the remaining bytes is a torn tail (never allocate
  from an untrusted length).
- bincode deserialization uses `with_limit(payload_len)`.
- `Revert { seq }` must follow `Commit { seq }` directly; it removes that frame.
  Any other placement is corruption.
- Commit `seq` values must be consecutive starting at 0.

### Overlay Semantics: Physical Row Space

Each table has a physical row space `[0, base_rows + appended_rows)`:

```
rowid:    0 ......... base_rows-1 | base_rows ......... base_rows+k-1
source:   main file rows          | log Insert ops, in commit order
```

- **rowid == physical index.** The vtable already reports `rowid = position`;
  this extends it. Rowids never change until compaction.
- **Insert** appends: rowid = `base_rows + appended.len()`.
- **Update** replaces the row's values in place (rowid and row order preserved).
- **Delete** tombstones the slot. Deleted rowids are never reused.
- Update/Delete of an unknown or already-deleted rowid is an error (during
  replay: log corruption).
- Every row must have exactly `columns.len()` values.

```rust
struct TableOverlay {
    base_rows: u64,
    deleted_base: BitVec,                 // tombstones over base rows
    updated_base: BTreeMap<u64, Vec<Value>>,
    appended: Vec<Option<Vec<Value>>>,    // None = deleted after insert
}
```

Merge helpers (all O(physical rows) per column):
- `physical_column(col, base_values) -> Vec<Value>`: physical space, deleted
  slots hold `Null` (never surfaced; masked out by `live_mask`).
- `live_mask() -> BitVec`: 1 = live row.
- `visible_column(col, base_values) -> Vec<Value>`: live rows only, rowid order.
  Used by crack/hatch/compact/etc.
- `live_row_count()`, `pending_counts()` for info/candle.

### Rebuild Extraction

The decode → `analyze_column` → `select_encoding` → encode loop moves from
`src/commands/relay.rs` into `eggdb_core::format::rebuild::encode_table()`.
`relay` and `compact` both call it. Relay output must be byte-identical to
before the move (existing relay tests enforce this).

## M14: eggdb-store

### Snapshot Open

`EggSnapshot::open(path, passphrase)` reads main + log and returns the main
bytes, parsed metadata, and one `TableOverlay` per table.

Consistency with a concurrent compaction: stat main → read main → read log →
stat main again. If the main file's identity changed (inode on unix, otherwise
length + mtime), retry (bounded). This prevents pairing an old main file with
an already-deleted log.

### Recovery Table

| Main checksum vs log | Log contents | Meaning | Action |
|---|---|---|---|
| no log file | — | no pending writes | empty overlays |
| base == main | any | normal | replay Commit frames; ignore a trailing Compacted marker (compaction crashed before rename) |
| base != main | has `Compacted` matching main | compaction crashed after rename, before log removal | treat log as absorbed (empty); next writer removes it |
| base != main | otherwise | log belongs to a different file (e.g. main re-laid) | **error**, never silently applied or dropped |

### Writer

- Exclusive OS lock on the log file (`std::fs::File::try_lock`, std since 1.89).
  On unix, after locking, verify the path still names the locked inode; retry
  if compaction replaced it.
- Lock is taken at transaction begin (first write), held until commit or
  rollback. Readers never lock. A second writer fails fast with a "busy" error.
- At lock time the writer replays any frames appended since its snapshot, so
  rowids and constraint checks are computed against the latest state.
- Log creation: open-or-create the log, take the lock, then (if empty, interrupted,
  or absorbed) truncate durably, write the header, fsync, fsync dir. Truncating
  durably *before* writing the header means old frames can never sit behind a
  header bound to a new main file.
- Append: cut the file back to the valid prefix, write the frame, `sync_data`. If
  that fails, truncate durably; if even that fails, the writer reports `is_uncertain`
  and the vtable refuses further work until reopened.

### Compaction

```
1. lock log; open snapshot; nothing pending -> done
2. merged columns -> rebuild::encode_table -> write_egg  (keeps source flags)
3. write data.egg.compact.tmp, fsync
4. append Compacted { checksum, length } to log, fsync
5. rename tmp -> data.egg, fsync dir
6. remove log, fsync dir, unlock
```

| Crash after step | On next open |
|---|---|
| 2-3 | main unchanged, log intact; stray tmp overwritten next compaction |
| 4 | base == main → replay normally, marker ignored |
| 5 | base != main, marker matches → log treated as absorbed |
| 6 | clean |

Compaction rejects encrypted files in this cut (writes to them are rejected,
so they never have a log).

## M15: Writable Virtual Table

### Arguments

```sql
CREATE VIRTUAL TABLE t USING egg('data.egg', 'users');                 -- read-only (default)
CREATE VIRTUAL TABLE t USING egg('data.egg', 'users', 'mode=rw');      -- writable
CREATE VIRTUAL TABLE t USING egg('data.egg', 'users', 'passphrase=x');
CREATE VIRTUAL TABLE t USING egg('data.egg', 'users', 'secret');       -- legacy positional passphrase
```

Extra arguments are `key=value` when the key is `mode` or `passphrase`;
otherwise a single positional argument is the legacy passphrase.
Writes on a read-only table fail with a message naming `mode=rw`.
Writes on encrypted files fail with a clear "not supported yet" error.

### Shared Per-Connection State

All egg vtables in one connection that point at the same canonical path share
one `SharedEgg` (main bytes, overlays, pending ops, lock, validators). It lives
in the module's `Aux`, which is per `register_egg_module(conn)` call, so there
are no process globals. This makes one SQL transaction across two tables of the
same egg produce one log frame (atomic), and reads the main file once per
connection instead of once per table.

### Transaction Mapping

| SQLite callback | Action |
|---|---|
| `xBegin` | take log lock (once per SharedEgg), catch up on new frames |
| `xUpdate` | validate → apply to working overlay → push to pending ops |
| `xSync` | append one Commit frame with all pending ops, fsync (first vtab only; others no-op) |
| `xCommit` | working state becomes committed; release lock |
| `xRollback` | discard pending ops; if already synced, append Revert + fsync; drop validators; release lock |

`xSync` is the durability point because SQLite propagates its errors, while
`xCommit` errors are ignored by SQLite. If a Revert cannot be written, the
SharedEgg is poisoned: every later operation errors until reopened.

### Constraint Enforcement

Per table, built lazily on the first write:

1. **Scratch table**: an in-memory SQLite connection runs the stored
   `original_ddl`. Each candidate row is inserted inside a savepoint with
   `RETURNING *`, then rolled back. This applies SQLite's own type affinity,
   NOT NULL, CHECK, and generated-column rules, and returns the normalized row,
   so the egg stores exactly what `hatch` would store.
2. **Key table**: an in-memory table holding only the columns of PRIMARY KEY /
   UNIQUE constraints (and `UNIQUE` indexes from `index_definitions`), keyed by
   egg rowid, with the same collations and unique indexes. Loaded once from the
   merged columns. Insert/update/delete mirror into it, so SQLite enforces
   uniqueness with its exact semantics (NULL handling, collations, 1 == 1.0).
3. **INTEGER PRIMARY KEY** (rowid alias): NULL is replaced with `max + 1`, like
   SQLite. At `i64::MAX`, error.
4. **DEFAULT** (verified in M15): SQLite *discards* DEFAULT clauses declared in a
   virtual table's schema (`pragma_table_xinfo` shows `dflt_value = NULL` for
   them), and no API tells `xUpdate` which columns an INSERT named. So an omitted
   column and an explicit NULL are indistinguishable. Chosen behavior: on INSERT
   only, a NULL in a column that has a DEFAULT is treated as omitted; the scratch
   INSERT leaves that column out and SQLite's own DEFAULT logic fills it
   (including `CURRENT_TIMESTAMP` and expressions, evaluated at insert time).
   UPDATE never applies defaults. The alternative (never applying defaults)
   would silently store NULL for every omitted `created_at DEFAULT
   CURRENT_TIMESTAMP`-style column, a far more common case than inserting an
   explicit NULL into a defaulted column.

Tables with partial unique indexes or DDL that cannot run in a fresh database
reject writes with a clear error (never silently skip enforcement).
Foreign keys are not enforced (SQLite's default is off).

### Filter Push-Down With Overlays

Encoding-level masks are computed on main-file rows only. Because SQLite
re-checks every constraint (`omit = false`), a mask may contain false
positives but **never false negatives**:

```
mask = encoding_mask(base rows)
     | updated_base rows        // new value may match even if old didn't
     & !deleted rows
     ++ all live appended rows  // never filtered by encoding
```

### Known Limitations

- **Statement atomicity inside explicit transactions.** rusqlite exposes no
  `xSavepoint/xRollbackTo`. Inside `BEGIN ... COMMIT`, a multi-row statement
  that fails partway keeps the rows it already wrote. In autocommit mode (how
  `egg query` runs) a failed statement rolls back entirely.
- **Conflict clauses.** `INSERT OR REPLACE/IGNORE` and `ON CONFLICT` behave as
  ABORT (error), never as silent divergence.
- **Explicit rowids.** `INSERT` with an explicit rowid, or `UPDATE` changing
  rowid, is rejected. Rowids are positions.
- **Dirty-read window.** Between `xSync` and a failing commit, another process
  may briefly observe a frame that is then reverted.
- **Explicit NULL into a defaulted column** gets the DEFAULT on INSERT (see
  Constraint Enforcement, item 4). SQLite would store NULL (or reject it for a
  NOT NULL column).
- **Connection snapshots.** A connection sees the file as of when it opened, plus
  its own writes. Other processes' commits become visible when it next writes
  (catch-up at `xBegin`) or reconnects. If another process compacts the file, the
  next write fails with a "reopen" error (`StoreError::Stale`).
- **AUTOINCREMENT** is treated like a plain INTEGER PRIMARY KEY (max + 1 over live
  rows); `sqlite_sequence` is not stored in `.egg` files.
- **Python bindings** read pending changes but cannot write.

## M16: CLI + Log-Aware Reads

- `egg compact <file.egg> [--zstd-level N]`: M14 compaction with a summary
  (rows before/after, size before/after).
- `egg query` / `egg shell` open vtables with `mode=rw`. Statements that return
  no columns run via `execute` and print "N rows changed" plus a hint to run
  `egg compact` when changes are pending.
- Log-aware read paths, all through `EggSnapshot`:
  `hatch` (eggdb-io), `crack`, `info`, `candle`, `diff`, `validate`
  (also checks log header/frames/binding), `web`, `relay`, `schema`
  (metadata only), Python bindings.
- `info` / `candle` show pending inserts/updates/deletes and live row counts.
- `lay`, `relay`, `incremental lay` refuse to write an output path that has a
  `.wal` sidecar (would orphan pending changes).

## Deferred (Not in This Cut)

- Writes to encrypted eggs (encrypt frames with the main key, random nonce).
- Automatic compaction at a size threshold.
- Schema evolution (add/drop/rename column).
- `egg append <source.sqlite>` bulk import (`INSERT ... SELECT` via ATTACH works today).
- Zone maps / M10 push-down interplay with overlays.

## Testing

### Unit / Property (eggdb-core)
- Log header + frame round-trip; torn tail at every byte offset of the last
  frame is discarded; flipped byte in a middle frame is an error.
- Revert placement rules; non-consecutive seq rejected.
- proptest: random op sequences applied to `TableOverlay` match a naive
  `Vec<Option<Row>>` model (visible rows, rowids, live counts).
- `rebuild::encode_table` output equals the pre-refactor relay output.

### eggdb-store
- Open without log; commit → reopen sees changes; torn tail truncated on next append.
- Each compaction crash state constructed by hand → correct recovery.
- Foreign log → error. Second writer → busy error.

### Vtable (differential)
- The same DML sequence runs against a plain SQLite table and an egg vtable;
  `SELECT` results must match after every statement.
- ROLLBACK undoes; multi-table transaction = one frame; read-only rejects writes.
- NOT NULL / UNIQUE / PRIMARY KEY / CHECK violations error; affinity applied;
  INTEGER PRIMARY KEY auto-assigns; DEFAULT honored.
- Filter regression: an updated row whose new value matches a pushed-down
  filter must be returned.

### End-to-End
- lay → DML via `egg query` → `crack` shows changes → `compact` → `hatch` →
  row-by-row equal to a SQLite copy that had the same DML applied.

### Fuzz
- `fuzz_wal_reader`: random bytes to the log parser never panic.
